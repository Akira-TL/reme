# Reme 技术可行性分析（第一轮）

- 日期：2026-08-01
- 状态：待样本视频与设备实测后复审
- 目的：在定义数据格式、事件规则或系统架构之前，判断项目关键链路是否具备比赛期内可验证的实现路径。

## 1. 当前已知条件

- 团队之后会提供一段含人体动作的视频。
- 可用硬件包括树莓派 4B 和一块涂鸦带屏开发板，但尚未确认它们是否必须承担姿态推理。
- 主故事倾向于隐私保护下的老人安全看护。
- 当前尚未拿到实际视频、目标电脑配置或树莓派内存版本。
- 团队已确认有可用的 MiMo API，因此不再把“是否能调用 MiMo”作为当前阻塞项。
- 隐私目标已明确：系统可以本地解码原始视频，但评委、家属和 MiMo 不应看到可轻易辨认人的原始画面；展示以骨骼、轮廓或强抽象画面为主。

因此，本报告当前重点从“路线是否存在”收敛为“指定视频中的人体姿态能否被稳定分类”。

## 2. 当前需要分别验证的四个问题

1. **人体姿态提取可行性**：实际视频中能否连续获得稳定的人体关键点。
2. **静态姿态分类可行性**：单帧或短窗口能否区分站立、坐姿、躺卧、弯腰/蹲姿和未知状态。
3. **时序事件分类可行性**：一段姿态序列能否区分正常坐下/躺下与跌倒式快速转变。
4. **隐私表达可行性**：是否能只展示骨骼、轮廓或强抽象画面，而不让观察者轻易辨认人的外观。

树莓派部署属于后续优化 Gate；MiMo API 已具备，当前只需明确它消费什么分类结果，不让它承担底层关键点提取。

## 3. 现有技术证据

### 3.1 离线视频转人体关键点：路线存在，实际效果待测

Google MediaPipe Pose Landmarker 官方接口支持 `VIDEO` 模式，要求逐帧输入视频帧及单调递增时间戳；其输出包含归一化图像坐标和世界坐标。当前官方 Pose Landmarker 定义 33 个姿态关键点。

- https://ai.google.dev/edge/api/mediapipe/python/mp/tasks/vision/PoseLandmarker
- https://ai.google.dev/edge/api/mediapipe/python/mp/tasks/vision/PoseLandmarkerResult
- https://ai.google.dev/edge/api/mediapipe/python/mp/tasks/vision/PoseLandmark

TensorFlow 官方 MoveNet 路线提供 17 个关键点，分 Lightning 和 Thunder 两种模型；官方教程直接覆盖图像和视频姿态推理。官方只说明其在多数现代桌面、笔记本和手机上可达到实时级速度，不能据此推断树莓派 4B 的表现。

- https://www.tensorflow.org/hub/tutorials/movenet
- https://github.com/tensorflow/tfjs-models/blob/master/pose-detection/src/movenet/README.md

**第一轮判断：**

- 在常规 x86 笔记本上，从离线视频提取单人姿态关键点，技术可行性高。
- 对团队即将提供的视频是否稳定，当前无法判断；关键变量包括机位、人体尺寸、遮挡、光照、动作速度、分辨率和压缩质量。
- 目前没有依据决定使用 17 点还是 33 点，也没有依据定义自有 JSON 格式。

### 3.2 基于姿态序列判断摔倒：研究上可行，比赛级可靠性未证明

已有研究使用 2D/3D 姿态序列进行摔倒检测，也有基于 MoveNet 的轻量方案；这说明路线在研究和原型层面可行。

- https://arxiv.org/abs/2107.14633
- https://arxiv.org/abs/2401.01587

但骨骼动作识别在开放场景中存在明显的泛化问题：未知动作、视角变化、遮挡和缺少场景上下文都会影响结果。相关开放集骨骼动作识别研究也明确把泛化列为核心难点。

- https://arxiv.org/abs/2312.06330

**第一轮判断：**

- 对一段经过选择、机位固定、动作明确的视频，做“演示级摔倒片段识别”可能可行。
- 仅靠少量手写角度阈值不能证明真实家庭环境中的摔倒检测能力。
- 在看过视频并完成关键点可视化之前，不应定义摔倒规则、准确率或支持动作数量。
- 若比赛需要可复现演示，可以先做“关键点提取 + 人工标注片段回放”；是否增加自动识别应由实测结果决定。

### 3.3 数据集可以辅助验证，但授权和域差异限制明显

UR Fall Detection Dataset 官方页面提供 30 段跌倒和 40 段日常活动序列，并包含 RGB、深度和加速度数据；授权为 CC BY-NC-SA 4.0，面向非商业学术用途。

- https://fenix.ur.edu.pl/~mkepski/ds/uf.html

NTU RGB+D 官方数据集包含 RGB、深度、红外和 3D 骨骼数据，但下载需注册并接受协议，使用范围为非商业学术研究；其数据量也远超比赛期快速验证的需要。

- https://rose1.ntu.edu.sg/dataset/actionRecognition/

**第一轮判断：**

- 公共数据集适合补充压力测试，不适合作为比赛现场 Demo 的唯一依据。
- 数据集中的模拟跌倒、年轻参与者、Kinect 视角与真实老人家庭场景存在域差异。
- 最安全的 Demo 素材仍是团队自录或明确获得授权的视频。

### 3.4 树莓派 4B：运行轻量推理存在路径，但当前不能承诺性能

树莓派 4B 使用四核 Cortex-A72 1.5 GHz 处理器，内存版本可能不同。Google LiteRT 官方文档支持 Raspberry Pi 3/4 的 ARMv7 和 aarch64 Python 运行时，说明部署通路存在。

- https://magazine.raspberrypi.com/articles/raspberry-pi-4-specs-benchmarks/
- https://ai.google.dev/edge/litert/guide/python
- https://ai.google.dev/edge/litert/build/cmake_pip

但 MediaPipe 当前稳定版 PyPI 页面展示的 Linux wheel 为 x86_64，未展示稳定 Linux aarch64 wheel；nightly 包存在 aarch64 wheel。这意味着直接在树莓派上采用 MediaPipe Python 可能遇到安装和稳定性风险。相比之下，MoveNet + LiteRT 更适合作为树莓派候选路线，但仍需在实际 Pi 上测量。

- https://pypi.org/project/mediapipe/
- https://pypi.org/project/mediapipe-nightly/

**第一轮判断：**

- 树莓派 4B 不是当前可以承诺的主推理平台。
- 第一轮应先在笔记本上验证视频和模型，再决定是否值得移植到 Pi。
- Pi 更可能承担“本地处理概念展示、结果转发或屏幕联动”，而不是未经实测就承担完整实时推理。

### 3.5 MiMo：远程调用可能可行，本地部署不现实

MiMo-V2-Flash 官方模型卡显示其为 309B 总参数、15B 激活参数的 MoE 模型，官方推荐的部署示例使用 SGLang、多 GPU 并提供 OpenAI 兼容接口；模型仓库体积约 313 GB。因此不能把它设计为树莓派或普通笔记本上的本地模型。

- https://huggingface.co/XiaomiMiMo/MiMo-V2-Flash
- https://github.com/XiaomiMiMo/MiMo-V2-Flash

MiMo 早期 7B 模型官方提供 vLLM 和 Transformers 运行方式，但是否能在团队现有机器上以可接受速度运行仍无实测证据。

- https://github.com/XiaomiMiMo/MiMo

**第一轮判断：**

- MiMo 集成是否可行，首先取决于比赛是否提供 API、密钥、模型地址和网络。
- MiMo 不应承担安全关键的底层姿态提取。
- 在没有 API 条件前，不能把“MiMo 自动决策”列为已确定闭环。
- 更合理的候选职责是：解释结构化检测结果、发起自然语言询问、生成家属摘要；是否采纳需后续单独验证。

## 4. 隐私主张需要重新表述

只要输入是普通视频，系统就必须在某个阶段访问和解码原始画面。因此当前不能声称“系统不处理原始视频”。能够争取证明的较窄主张是：

- 视频在本地离线读取；
- 不把原始帧发送给 MiMo 或云端；
- 不额外导出原始帧；
- 对外展示和后续分析只使用骨骼或派生数据；
- 原始视频文件本身由用户主动提供并受控保存。

这些主张仍需通过网络监测、文件输出检查和代码路径审计验证。

## 5. 第一轮可行性结论

| 子问题 | 当前判断 | 置信度 | 主要缺口 |
|---|---|---:|---|
| 笔记本离线视频转单人关键点 | 可行 | 高 | 尚无实际视频测试 |
| 从指定视频形成骨骼隐私视图 | 大概率可行 | 中高 | 遮挡、机位、画质未知 |
| 自动识别一个明确摔倒片段 | 可能可行 | 中 | 尚未定义标注和评价方法 |
| 泛化到真实老人家庭摔倒检测 | 当前不可证明 | 高 | 数据、训练、跨场景验证不足 |
| 树莓派 4B 完整姿态推理 | 未知 | 中 | 运行时、内存、FPS 尚未实测 |
| MiMo 远程解释/对话 | 条件可行 | 中 | API、网络、延迟未知 |
| MiMo 本地运行在 Pi/普通笔记本 | 不可行或极不现实 | 高 | 模型规模远超设备能力 |

## 6. 正确的下一步：先验证姿态分类，再定义产品闭环

拿到视频后，第一阶段先验证“姿态提取与姿态分类是否可用”。不提前定义告警策略，也不把某组阈值包装成通用摔倒算法。

### 实验 A：视频质量与可解码性

记录：

- 文件格式、编码、分辨率、帧率、时长；
- 人体占画面比例；
- 动作类型和时间段；
- 遮挡、离开画面和镜头切换情况。

### 实验 B：两条姿态模型路线对比

至少比较：

- MediaPipe Pose Landmarker；
- MoveNet SinglePose Lightning。

不提前选模型。对同一视频记录：

- 成功检测人体的帧比例；
- 关键点连续性和明显跳点；
- 摔倒、坐下、躺下等片段的可视化效果；
- 平均与 P95 单帧处理时间；
- CPU 和内存；
- 安装与模型授权风险。

### 实验 C：静态姿态分类

第一版候选标签不是最终产品承诺，而是用于标注和比较模型的工作集合：

- `standing`：站立或直立；
- `sitting`：坐姿；
- `lying`：躺卧；
- `bending_or_crouching`：弯腰、下蹲或低姿态；
- `unknown`：遮挡、人体离画或关键点置信度不足。

先比较两条低成本路线：

1. 基于骨骼几何特征的透明基线，例如躯干方向、髋膝踝相对位置、身体长宽比；
2. 使用标注关键点窗口训练轻量分类器。

输出混淆矩阵，重点观察 `lying` 与 `sitting`、`lying` 与 `bending_or_crouching` 的混淆。

### 实验 D：时序事件分类

“跌倒”不作为单帧姿态标签，而作为时间窗口事件：

- `normal_transition`：正常坐下、起身或躺下；
- `fall_like_transition`：短时间内由直立转为低位/水平，且运动速度、重心变化与后续状态符合候选模式；
- `uncertain_transition`：证据不足或遮挡严重。

先使用可解释特征建立基线；若样本量允许，再比较轻量时序分类器。ST-GCN 等骨骼时序模型证明了骨骼序列可用于动作识别，但比赛阶段是否采用深度时序模型取决于样本量和实测，而不是论文指标。

### 实验 E：MiMo API 接入边界

MiMo API 已可用，候选输入为：

- 当前姿态标签及置信度；
- 最近数秒的姿态变化；
- 候选事件及可解释特征；
- 是否收到用户回应。

MiMo 候选职责是生成自然语言说明、询问和摘要。底层关键点提取与第一层姿态分类仍由专用视觉/时序模块完成，以保证可测量和可复现。

### 实验 F：树莓派作为后续 Gate

在笔记本路线成功后再移植和测量；树莓派失败不阻塞主 Demo。

## 7. Go / No-Go 条件

在完成样本视频实验前，不设置虚构的 FPS 或准确率门槛。实验完成后依据比赛演示需求共同设定。

当前 Gate 为：

- **Go：** 至少一种姿态提取模型能形成连续骨骼，并且静态姿态分类在目标视频上能稳定区分站、坐、躺和未知；跌倒式转变至少能在标注片段上复现。
- **Conditional Go：** 骨骼与静态姿态分类可用，但正常躺下和跌倒式转变难以稳定区分；主 Demo 展示姿态状态与隐私化画面，不宣称可靠跌倒检测。
- **No-Go：** 人体过小、遮挡严重或镜头切换频繁，导致骨骼不连续，静态姿态也无法可靠分类；需要更换视频或重新设计演示输入。

## 8. 对仓库现有实现的处理意见

提交 `61f2a9b` 中的动作 JSON、事件阈值和分级响应属于在可行性验证前做出的假设，**不构成已接受架构或产品规格**。在完成本报告的实验 Gate 前：

- 不继续扩展该实现；
- 不使用其字段或阈值约束视频提取方案；
- 不在 PPT 中把它作为已验证能力；
- 后续根据实测结果决定删除、重写或仅保留为一次废弃原型记录。
