## 1. 使用原则

两份附件用于统一产品目标、比赛叙事和候选技术路线，但不自动覆盖实测结果，也不把尚未验证的能力变成既定事实。

后续区分四类信息：

1. **已测事实**：已有可复现命令和测量结果。
2. **附件共识**：两份材料方向一致，可作为当前产品假设。
3. **候选决策**：材料提出但尚未通过实验或接口验证。
4. **冲突决策**：材料之间表述不一致，需要单独选择。

## 2. 已测事实

### 2.1 姿态提取 Gate 已通过

目标视频 `148703662.mp4` 已完成 LiteRT + MoveNet SinglePose Lightning 全帧测试：

- H.264，1280×720，30 FPS，79 秒，2370 帧；
- MoveNet Lightning FP16 + 逐帧跟踪裁剪达到 100% 躯干覆盖；
- 2369/2370 帧的双肩、双髋、双膝和双踝置信度达到实验阈值；
- `Interpreter.invoke()` 平均 3.956 ms，P95 4.850 ms；
- 已生成完整黑底骨骼视频和关键点 JSONL；
- 原始帧未作为实验输出持久化。

证据位置：

- `.scratch/litert-movenet-feasibility/spec.md`
- `.scratch/litert-movenet-feasibility/results/2026-08-01-video-148703662.md`

### 2.2 尚未验证

上述结果不能证明：

- 站立、坐姿、躺卧、弯腰等姿态分类准确；
- 正常躺下可以与跌倒式转变区分；
- 对其他人物、房间、机位或遮挡条件具有泛化能力；
- Raspberry Pi 4B 达到可接受性能；
- MiMo API 的结构化输出、视频理解、延迟和降级路径已跑通。

## 3. 两份附件的共同方向

以下内容在核心产品文档与 MiMo 可行性报告中基本一致，可作为当前产品假设：

1. Reme 是可接入现有设备的软件能力层，不以自研新硬件为主线。
2. 唯一主场景是银发家庭关怀，不在比赛主线扩展儿童、宠物、车辆或机构取证。
3. 家属端不应获得持续清晰监控画面；默认交付事件、对话摘要和行动结果。
4. 标准闭环为：本地感知 → 事件或候选变化 → 规则初筛 → MiMo 判断与沟通 → 家庭行动 → 处理反馈。
5. 主演示候选为：午餐时长时间静坐/未进食 → 自然询问 → 发现牙齿不适 → 征得同意 → 家属行动卡。
6. 高风险安全规则优先于 MiMo；MiMo 不得取消、压制或延迟确定性告警。
7. MiMo 的价值重点是介入判断、沟通方式、需求理解、结果分流和行动建议，而不是替代底层姿态模型。
8. 比赛应具备 live / mock(scripted) / record 三种演示保障模式。
9. 所有 MiMo 输出必须经过结构校验和降级处理。
10. 未经实测，不宣称姿态准确率、误报率、低延迟或医疗效果。

## 4. 需要保留为候选、不能直接冻结的内容

### 4.1 姿态分类标签与事件集合

核心产品文档提出 P0 包含正常、长时间静止、疑似跌倒。该集合适合作为实验目标，但目前只通过了关键点提取 Gate。

需要先验证：

- 静止是否通过关键点速度和持续时间稳定识别；
- 坐姿、躺卧、弯腰和遮挡是否会造成误触发；
- 跌倒采用规则、轻量时序分类器，还是仅作为剧本事件；
- 是否需要 `unknown` / `uncertain` 拒判状态。

### 4.2 MiMo 固定合同

核心产品文档给出一组候选字段：

- 事件输入：`event_type / duration / zone / pose_state / motion_level / confidence`
- 上下文输入：`time_context / baseline_summary / recent_events / dialogue_history`
- 决策输出：`risk_level / need_dialogue / dialogue_goal / opening / family_notification`
- 行动输出：`reason_summary / action_card / consent_required / fallback_action`

这些字段可作为 API Spike 的起点，但在姿态分类和 MiMo Schema 实测前，不作为永久领域合同。

### 4.3 主演示的实时程度

产品文档以笔记本摄像头实时输入为主模式，但当前已测证据来自离线视频。后续需要明确：

- 比赛是否必须实时采集；
- 离线视频实时速率回放是否足够；
- 摄像头现场动作是否仅作为可选增强；
- 现场光线或人物站位失败时如何无缝切到脚本模式。

## 5. 两份附件之间的关键冲突

### 冲突 A：MiMo 是否接收视觉数据（已解决）

2026-08-01 团队决定取消“原始帧不得发送给 MiMo”的绝对限制，并通过 ADR-0003 允许 B 在需要视觉上下文时发送选定关键帧或短视频。

当前保留两条可测试路径：

- **路径 S（Structured）**：本地姿态/事件 → MiMo 文本 JSON；
- **路径 V（Visual）**：结构化上下文 + 最小关键帧/短视频 → MiMo 多模态理解。

Visual 路径不等于持续上传完整视频。每次请求应记录视觉类型、采样范围、帧数或片段时长，并在 PPT 和 Demo 中明确说明视觉内容会发送给 MiMo。

后续仍需比较两条路径的输出稳定性、响应时间、网络依赖、隐私成本、工程复杂度和现场可复现性，以决定比赛主路径与降级路径。

### 冲突 B：谁负责发现“未进食/触碰面颊”

主演示需要理解“长时间未进食、多次触碰面颊、牙疼”等语义。

仅依赖 17 点人体骨骼，可能无法可靠判断：

- 食物是否减少；
- 是否触碰特定面部区域；
- 是普通摸脸还是牙齿不适。

因此需要验证三种候选：

1. 本地姿态只发现“异常静坐”，后续通过对话确认原因；
2. 本地候选事件 + MiMo 关键帧/短视频补充场景语义；
3. 比赛中通过剧本事件触发，不宣称视觉系统自动识别牙疼线索。

附件没有足够证据直接选定其中一种。

### 冲突 C：“开发冻结版”与当前讨论方式

核心产品文档自称“唯一事实源”和“比赛开发冻结版”，但团队已明确要求不要对前期想法做绝对判断。

因此本次移交采用以下解释：

- 文档中的定位、主场景和产品原则是当前强基线；
- 技术实现、MiMo 输入方式、实时模式和事件分类仍由实验决定；
- 任何修改应记录原因和证据，而不是因“冻结”二字禁止复审。

## 6. 推荐后续顺序

### Phase 1：完成姿态分类可行性

基于已经生成的关键点 JSONL：

1. 人工标注目标视频中的站立、坐姿、低位/躺卧、弯腰/下蹲、未知区间；
2. 标注动作转变和持续静止区间；
3. 建立可解释几何特征基线；
4. 评价每类 precision / recall / F1、混淆矩阵和拒判率；
5. 决定“长时间静止”和“疑似跌倒”分别使用规则、分类器还是剧本触发。

### Phase 2：MiMo API 双路径 Spike

使用同一主演示场景测试：

- Structured：结构化事件 + 上下文 → 固定决策 JSON；
- Visual：最小关键帧/短视频 + 上下文 → 固定事件/决策 JSON。

必须记录：

- API 模型与参数；
- 首次 Schema 校验通过率；
- 重试后的通过率；
- 平均和 P95 响应时间；
- 输出字段漂移；
- 超时、断网和非法输出的降级结果；
- 实际发送到网络的内容。

### Phase 3：冻结比赛数据流

在 Phase 1 和 Phase 2 证据基础上，明确：

- 主模式使用 Structured 还是 Visual；
- 另一条路径是增强模式、降级模式还是删除；
- MiMo 输入/输出合同；
- 三类分流触发方式；
- 高风险规则的最小范围；
- 家属行动卡字段；
- 隐私演示口径。

### Phase 4：实现比赛闭环

再进入：

- 老人端对话；
- 家属行动卡；
- live / mock / record；
- 故障注入；
- 连续运行测试；
- 路演脚本和录屏。

## 7. 当前建议的工作前沿

可立即开始且互不冲突的两项工作：

1. **姿态分类标注与基线实验**：已有关键点数据，不依赖 MiMo。
2. **MiMo API Schema Smoke Test**：先用手工事件 JSON 验证 API、结构化输出和降级，不依赖最终分类器。

暂不建议直接开始：

- 完整老人端/家属端 UI；
- 固定全部事件字段；
- 在 Pi 上迁移完整链路；
- 自动识别牙疼或医疗状态；
- 让 MiMo 自由决定高风险报警。

## 8. 移交结论

项目已具备一个可靠的骨骼提取基础，但产品闭环中的两个关键问题仍需并行验证：

- 本地姿态序列能稳定提供哪些事件候选；
- MiMo 在只接收事件与接收最小视觉信息时，哪条路径更稳定、更能体现产品价值。

因此后续不是推翻前期方向，也不是机械执行“冻结版”，而是以附件为产品基线、以实验为技术裁决依据。
