# Reme 软件演示端工作规格（成员 C）

- Type: spec
- Status: open
- Owner: C
- Date: 2026-08-01
- 工作目录：`.scratch/software-demo/`
- 现有可复用原型：`.scratch/motionbert-offline-demo/`

## 1. 文档目的

本文件用于明确成员 C 在 Reme 比赛项目中的工作边界、依赖接口、开发顺序、交付物和验收标准。

C 的职责不是训练姿态分类模型，也不是决定 MiMo 的风险策略，而是把 A 和 B 的结果组合成一个稳定、直观、可重复演示的软件端。

一句话职责：

> C 负责将 A 输出的动作节点与分类结果可视化，并接入 B 输出的 MiMo 推理与主动交互结果，形成完整的软件 Demo。

## 2. 为什么写在这里

根据仓库 `AGENTS.md`、本地 Issue Tracker 规范和 Ask Matt 流程：

- 这是一个需要跨多个开发阶段完成的模块，不适合只保留在聊天记录中；
- 当前界面和接口仍属于比赛规格与验证阶段，尚未成为正式产品架构；
- 因此规格放在 `.scratch/software-demo/spec.md`；
- 后续若需要拆分开发任务，应放在 `.scratch/software-demo/issues/`；
- 只有当数据合同、界面边界和演示流程通过验收后，才考虑将稳定代码迁移到正式目录。

## 3. 当前事实与工作起点

### 3.1 已经完成并可复用的内容

现有 MotionBERT 离线双屏原型已经验证：

- 测试视频可以在本地 Web 页面播放；
- MoveNet 2D 关键点可以转换为 MotionBERT 3D 骨架；
- 目标视频 2370 帧均已生成三维姿态；
- 视频播放、暂停、拖动和 3D 骨架能够同步；
- 3D 场景支持旋转、缩放、正视、侧视、俯视和重置；
- 本地 HTTP、Three.js 和无头 Chromium 验收已经通过；
- 现场可以采用预计算数据，不需要重新运行 MotionBERT。

现有代码位于：

```text
.scratch/motionbert-offline-demo/
├── index.html
├── app.js
├── styles.css
├── server.py
├── infer_motionbert.py
├── acceptance_test.py
├── README.md
└── spec.md
```

C 不需要从零重新实现 3D 骨架，应优先复用该原型。

### 3.2 仍未冻结的内容

以下内容当前不能假设已经确定：

- A 最终输出的姿态类别集合；
- A 最终输出的 JSON/JSONL 字段；
- 跌倒、长时间静止等事件的最终判断方式；
- B 最终使用 Structured 路径还是 Visual 路径调用 MiMo；
- B 的最终输入输出合同；
- 风险等级和主动交互策略的最终规则；
- 比赛最终使用实时模式还是离线回放模式。

因此，C 的软件端必须通过适配层接入 A/B，不能把临时字段硬编码到所有页面组件中。

## 4. C 的工作范围

C 的工作分为六个模块：

1. A 数据接入；
2. 视频与骨架可视化；
3. B 推理结果接入；
4. 主动交互和隐私状态展示；
5. 比赛演示模式与故障降级；
6. 向 D 提供产品展示素材。

## 5. C 不负责的内容

### A 负责

- 原始视频处理；
- 人体关键点提取；
- 姿态分类训练、测试和调试；
- 姿态类别、置信度和时序结果；
- 2D/3D 动作节点数据的生成。

### B 负责

- MiMo API 调用；
- 隐私状态判断；
- 风险等级推断；
- 是否主动交互的决策；
- 老人端询问内容；
- 家属端通知内容；
- 在线推理和离线推理结果。

### D 负责

- 产品定位；
- 作品申报内容；
- PPT；
- 路演故事和逐字稿；
- 商业价值、创新性和用户体验表达；
- 最终现场讲解组织。

### C 不应越界

- 不在前端重新训练或修改 A 的分类模型；
- 不在前端复制一套与 B 不一致的风险决策逻辑；
- 不自行定义医疗结论或真实报警规则；
- 不把单目 3D 骨架描述为真实空间坐标或医学测量；
- 不隐藏模型失败、低置信度或接口不可用状态；
- 不把规划中的功能展示成已经完成的功能。

## 7. A → C 数据接口

A 至少需要向 C 提供以下内容：

- 原始演示视频；
- 场景 ID；
- 视频时间戳；
- 帧编号；
- 2D 关键点；
- 3D 关键点，如该场景可用；
- 姿态分类；
- 姿态置信度；
- 姿态持续时间；
- 关键点可见性或数据可用状态。

候选数据示例：

```json
{
  "schema_version": "candidate-v1",
  "scene_id": "fall_demo",
  "timestamp_ms": 12500,
  "frame_index": 375,
  "person_detected": true,
  "pose_state": "lying",
  "pose_confidence": 0.91,
  "pose_duration_ms": 5200,
  "motion_level": "low",
  "availability": "available",
  "keypoints_2d": [],
  "keypoints_3d": []
}
```

注意：该结构只是 C 端适配器的候选输入，不是已经冻结的领域合同。A 的实验结果评审后才能冻结字段。

### C 对 A 接口的要求

- 时间单位必须明确；
- 视频帧率必须明确；
- 关键点顺序和骨架连接关系必须明确；
- 缺失关键点必须有明确表示；
- `unknown`、无人或低置信度必须能够表达；
- 同一段视频的数据必须可以稳定复现；
- C 不应该通过猜测字段含义完成接入。

## 8. B → C 数据接口

B 至少需要向 C 提供：

- 当前隐私状态；
- 当前风险等级；
- 是否需要主动交互；
- 当前系统动作；
- MiMo 判断原因；
- 老人端询问内容；
- 家属端通知内容；
- 当前结果来源；
- 推理是否可用；
- 决策时间轴事件。

候选数据示例：

```json
{
  "schema_version": "candidate-v1",
  "timestamp_ms": 12500,
  "privacy_state": "normal",
  "risk_level": 2,
  "should_interact": true,
  "action": "check_in",
  "reason": "检测到低位姿态并持续静止，需要先进行本地询问",
  "message_to_elder": "您还好吗？需要我联系家人吗？",
  "message_to_family": null,
  "inference_mode": "live",
  "availability": "available"
}
```

### C 对 B 接口的要求

- 返回结构化 JSON，而不是只返回一整段自然语言；
- 必须能表示加载中、超时、失败和离线降级；
- 必须注明结果来自 `live`、`mock` 还是 `record`；
- 风险等级和动作名称应保持稳定；
- B 的业务规则应集中在 B 端，C 只负责渲染和触发交互事件；
- 如果 B 的 MiMo 路径发生变化，C 的页面组件不应整体重写。

## 9. 软件端目标页面

建议使用一个单页演示界面，减少现场切换风险。

### 9.1 页面结构

```text
┌─────────────────────────────────────────────────────────┐
│ Reme 当前模式 / 场景选择 / Demo 状态                    │
├──────────────────────────┬──────────────────────────────┤
│ 原始视频或隐私遮挡区域   │ 2D / 3D 骨架可视化区域       │
│                          │                              │
├──────────────────────────┼──────────────────────────────┤
│ 姿态与感知状态           │ MiMo 推理与系统决策           │
│ - 姿态类别               │ - 隐私状态                    │
│ - 置信度                 │ - 风险等级                    │
│ - 持续时间               │ - 当前动作                    │
│ - 数据可用状态           │ - 判断原因                    │
├──────────────────────────┴──────────────────────────────┤
│ 主动交互区 / 家属通知 / 决策时间轴                       │
└─────────────────────────────────────────────────────────┘
```

### 9.2 信息优先级

第一优先级：

- 当前是否需要干预；
- 当前是否处于隐私保护状态；
- 系统正在采取什么行动。

第二优先级：

- 当前姿态；
- 姿态持续时间；
- 模型置信度；
- MiMo 判断原因。

第三优先级：

- 帧编号；
- 原始关键点坐标；
- 调试日志；
- 详细性能数据。

比赛界面不能把所有调试信息放在主视觉区域。

## 10. 功能模块要求

### 10.1 视频播放模块

必须支持：

- 播放和暂停；
- 拖动时间轴；
- 重播；
- 场景切换；
- 当前时间显示；
- 与关键点和状态数据同步；
- 视频加载失败提示。

### 10.2 2D 骨架模块

必须支持：

- 按时间绘制人体节点；
- 按正确拓扑连接骨架；
- 与原视频同步；
- 隐藏低置信度节点；
- 无人或数据不可用时显示明确状态；
- 不将骨架错位或上一帧残留伪装成有效结果。

### 10.3 3D 骨架模块

优先复用 `.scratch/motionbert-offline-demo/`：

- 播放、暂停和拖动同步；
- 支持旋转、缩放和预设视角；
- 显示单目根节点相对三维估计的能力边界；
- 3D 数据不可用时可切换至 2D，不阻断整个 Demo。

### 10.4 姿态状态模块

展示：

- 姿态名称；
- 姿态置信度；
- 姿态持续时间；
- 运动状态；
- 数据是否可用；
- `unknown` 或不确定状态。

界面不得把低置信度结果表现为确定结论。

### 10.5 MiMo 决策模块

展示：

- 当前隐私状态；
- 当前风险等级；
- 是否主动交互；
- 当前动作；
- 判断原因；
- 推理模式；
- MiMo 是否可用。

### 10.6 主动交互模块

至少支持以下演示输入：

- 老人回应正常；
- 老人请求帮助；
- 老人无回应；
- 重新开始当前场景。

C 将用户操作传给 B，由 B 返回下一步决策；C 不在页面中自行推断风险升级。

### 10.7 家属通知模块

当 B 返回通知动作时，页面展示：

- 事件时间；
- 当前状态；
- 系统已经执行的动作；
- 给家属的通知内容；
- 建议下一步行动；
- 结果来源和可用状态。

### 10.8 决策时间轴

时间轴应记录：

- 姿态状态发生变化；
- 隐私状态发生变化；
- 风险等级发生变化；
- 系统发起询问；
- 用户响应；
- 家属通知；
- 推理失败或进入降级模式。

时间轴必须是系统事件，不应展示未经约束的内部思维过程。

## 11. 隐私与展示边界

ADR-0001 已接受以下边界：

- 原始视频仅在本地处理；
- 原始帧不默认写入磁盘；
- 原始帧不发送给决策 Agent；
- 下游优先使用关键点、姿态分类和派生状态。

因此 C 端必须：

- 通过本地服务播放演示视频；
- 不增加视频上传功能；
- 不增加默认截图留存功能；
- 隐私模式下模糊、遮挡或关闭清晰原图；
- 保留骨架、状态和必要的系统反馈；
- 在界面中区分“本地原视频展示”和“发送给 MiMo 的信息”。

如果团队后续决定验证 MiMo Visual 路径，必须先更新对应 ADR 或形成新的实验说明。C 不应自行默认原始帧可以发送到云端。

## 12. 三个比赛场景

### 场景一：正常活动

输入：

- 视频中的站立、行走或坐姿片段；
- A 返回正常姿态；
- B 返回无需主动交互。

C 展示：

- 原视频和骨架同步；
- 正常姿态状态；
- 风险等级为低或正常；
- 系统状态为“不打扰”。

验收重点：系统不是看到人就不断弹窗。

### 场景二：隐私保护

输入：

- B 返回敏感隐私状态，或使用明确标记的比赛脚本事件；
- 该状态的触发方式必须在界面或讲解中诚实标注。

C 展示：

- 清晰原图被模糊、遮挡或关闭；
- 骨架和必要状态继续可见；
- 页面明显显示“隐私保护中”；
- 不展示不必要的家庭环境或人物细节。

验收重点：评委一眼看出系统正在主动减少暴露。

### 场景三：异常关怀

输入：

- A 返回低位、躺卧、异常转变或其他候选状态；
- B 返回主动询问；
- 用户在页面选择正常、求助或无回应。

C 展示：

1. 姿态和风险状态变化；
2. 系统主动询问老人；
3. 用户回应被发送给 B；
4. B 返回解除、继续观察或通知家属；
5. 页面更新时间轴和通知卡片。

验收重点：演示完整闭环，而不是只显示“检测到跌倒”。

## 13. Demo 运行模式

C 必须支持三种模式：

### Live

- 实际读取 A 的结果；
- 实际调用 B 的接口；
- 用于开发联调和条件允许时的现场展示。

### Mock

- 使用固定姿态数据和固定 B 返回值；
- 用于页面开发、交互测试和现场网络异常降级；
- 页面必须明确显示 `MOCK`，不能伪装为实时模型结果。

### Record

- 播放已经完整运行过的录制结果；
- 用于最坏情况下的路演兜底；
- 页面或讲解必须说明这是预录演示。

模式切换应由一个明确入口完成，不能临场修改代码。

## 15. C 的开发顺序

### Phase C0：复核现有原型

目标：确认现有 MotionBERT 双屏 Demo 在当前机器仍可运行。

任务：

- 启动现有本地服务器；
- 检查视频和 3D 数据路径；
- 检查播放、暂停、拖动和视角控制；
- 运行现有验收脚本；
- 记录缺失数据或环境依赖。

完成条件：现有原型可重复启动，或明确列出阻塞项。

### Phase C1：冻结 C 端适配器输入

目标：让 C 可以在 A/B 未完全完成时继续开发。

任务：

- 与 A 对齐最小姿态数据；
- 与 B 对齐最小决策数据；
- 建立候选 Schema 和适配器；
- 建立正常、隐私、异常三个 fixture；
- 对缺失字段给出明确错误。

完成条件：页面可以使用 fixture 跑通，不依赖 A/B 在线。

### Phase C2：完成可视化主链路

目标：将原视频、2D/3D 骨架和姿态状态同步展示。

任务：

- 复用 3D 原型；
- 增加 A 的姿态状态和置信度；
- 增加 2D 降级视图；
- 统一视频时间与数据索引；
- 处理 seek、pause、restart 和场景切换。

完成条件：三个 fixture 均可同步回放，状态无明显残留或错位。

### Phase C3：接入 B 和主动交互

目标：形成感知 → 推理 → 交互闭环。

任务：

- 接入 B 的结构化输出；
- 展示隐私、风险、动作和原因；
- 实现老人回应操作；
- 将回应发送给 B；
- 展示家属通知；
- 记录决策时间轴。

完成条件：异常场景可以完成至少两条分支：安全回应和无回应升级。

### Phase C4：演示模式与故障降级

目标：现场任何单点失败都不应导致无内容可讲。

任务：

- 支持 Live / Mock / Record；
- 增加加载、超时、不可用和降级状态；
- 增加一键重置；
- 增加场景快速切换；
- 准备本地资源和离线数据；
- 准备完整录屏。

完成条件：断开网络后 Mock 或 Record 仍能完成三场景演示。

### Phase C5：交给 D 进行路演整合

目标：让 D 可以基于真实软件制作 PPT 和讲解。

C 向 D 提供：

- 软件入口和启动方式；
- 三个场景的固定操作步骤；
- 每个场景的截图；
- 完整演示录屏；
- 软件能够展示的真实功能；
- 尚未完成或仅 Mock 的功能；
- 能力边界和风险说明。

完成条件：D 的 PPT、路演词和软件状态名称完全一致。

## 16. 工作优先级

### P0：比赛必须完成

- 现有 3D 原型可运行；
- 原视频与骨架同步；
- 姿态状态展示；
- B 结构化结果接入；
- 主动询问和用户回应；

## 17. 验收标准

### 功能验收

- [ ] 页面可以通过一条命令启动；
- [ ] 原视频可以播放、暂停、拖动和重播；
- [ ] 骨架与视频基本同步；
- [ ] A 的姿态分类和置信度可以显示；
- [ ] B 的隐私、风险和决策结果可以显示；
- [ ] 页面可以模拟老人正常回应；
- [ ] 页面可以模拟老人无回应；
- [ ] 无回应后可以展示家属通知；
- [ ] 隐私状态可以隐藏或模糊清晰视频；
- [ ] 三个场景可以快速切换；
- [ ] 页面可以一键重置；
- [ ] Mock 模式可以在无网络环境完整运行；
- [ ] Record 模式或完整录屏可以作为最终兜底。

### 可靠性验收

- [ ] 连续完整演示三次不出现阻断性错误；
- [ ] 页面刷新后能够恢复初始状态；
- [ ] 视频 seek 后不会继续显示旧状态；
- [ ] A 数据缺失时显示 unavailable，而不是复用旧结果；
- [ ] B 超时时显示降级状态，而不是无限等待；
- [ ] 3D 不可用时可以降级到 2D；
- [ ] 网络断开不影响 Mock 和 Record；
- [ ] 页面明确标注 Live、Mock 或 Record。

### 表达验收

- [ ] 页面主视觉首先说明当前状态和系统行动；
- [ ] 页面不把调试字段作为主要内容；
- [ ] 页面明确展示隐私保护状态；
- [ ] 页面明确展示不确定或能力不可用；
- [ ] 页面不出现医疗诊断或保证性表述；
- [ ] 页面说明 3D 是单目根节点相对估计；
- [ ] D 可以在 60–90 秒内使用页面讲完三个场景。

## 18. 风险与应对

| 风险 | C 的应对方式 |
|---|---|
| A 的字段持续变化 | 使用 pose adapter，避免组件直接读取原始字段 |
| B 的接口未完成 | 使用 decision fixture 和 Mock adapter 开发 |
| MiMo 网络不稳定 | 提供 Mock 和 Record 模式 |
| 3D 文件丢失 | 比赛前复制到受控的本地 artifacts 目录，并保留 2D 降级 |
| 视频和骨架不同步 | 统一以视频 currentTime 为主时钟，不使用独立计时器累加 |
| seek 后状态残留 | 每次 seek 和 scene reset 重建派生状态 |
| 低置信度姿态误导评委 | 显示置信度和 unknown/unavailable |
| 页面信息过多 | 按当前行动、姿态状态、调试信息分三级展示 |
| D 的 PPT 与功能不一致 | C 每次冻结 Demo 后提供功能清单、截图和录屏 |
| 临场操作复杂 | 固定场景入口、一键重置、预设操作脚本 |
