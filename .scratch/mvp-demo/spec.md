# Reme MVP Demo Spec

**Status:** rejected draft — written before feasibility analysis

> Do not implement or extend this specification. Its motion schema, fall logic, staged response, and MiMo boundary were assumed before the source video and target environments were tested. The active document is `.scratch/feasibility/feasibility-analysis.md`.

## Problem Statement

Families want timely awareness when an older adult may be in danger, but routine monitoring with a clear camera feed exposes clothing, body detail, facial detail, and the private state of the home. The hackathon team needs a credible 60–90 second demonstration that shows a safer observation model and a complete response path without claiming clinically validated fall detection.

## Solution

Reme consumes derived human-motion data rather than depending on a live camera. A motion-data adapter reads normalized pose observations from JSON/JSONL or another agreed exchange format; deterministic event logic converts a sequence of observations into an event candidate; a deterministic safety policy chooses the required response stage. MiMo may explain or phrase the response, but it does not override mandatory safety escalation in the MVP.

The first implemented tracer bullet uses a synthetic pose stream. A later ticket adds offline video-to-motion extraction for the human video supplied by the team. The video is an input source for generating motion data, not part of the core decision pipeline.

The judge-facing demo sequence is:

1. Show the privacy boundary: only motion landmarks and machine-readable state enter the core pipeline; raw pixels are absent from event and decision processing.
2. Run normal upright observations and show that no event is emitted.
3. Run a reproducible fall-like transition and emit a `possible_fall` event candidate with supporting measurements.
4. Show a local voice check-in decision.
5. Simulate no response and show a family-notification decision.
6. Show an audit summary stating which adapter ran, whether raw frames were persisted, and whether network access occurred.

## User Stories

1. As an older adult, I want routine monitoring to hide my appearance and room details, so that I can retain dignity at home.
2. As an older adult, I want the system to ask me locally before escalating, so that normal situations do not immediately alarm my family.
3. As a family member, I want a clear notification after a likely fall and no response, so that I know when to check in.
4. As a judge, I want to see the full path from derived observation to response, so that I can understand the product rather than only a slide deck.
5. As a judge, I want synthetic and live capabilities labelled honestly, so that I can distinguish demonstrated behaviour from planned behaviour.
6. As a developer, I want perception and decision logic separated by a versioned contract, so that camera/model adapters can change without rewriting safety policy.
7. As a developer, I want deterministic event fixtures, so that fall-like and normal sequences can be reproduced during development and judging.
8. As a developer, I want event candidates to carry supporting measurements, so that decisions are explainable and debuggable.
9. As a developer, I want low-visibility observations to produce an unavailable or review state rather than a confident event, so that uncertainty is visible.
10. As a presenter, I want one command to run the scripted demo, so that the demonstration is reliable under time pressure.
11. As a presenter, I want the demo output to show no raw-frame persistence and no network activity in the synthetic path, so that the privacy claim is inspectable.
12. As a future integrator, I want a small pose-observation interface, so that offline video extractors, motion-capture exports, or manually prepared fixtures can feed the same seam.
13. As a future MiMo integrator, I want structured decisions and context, so that MiMo can generate natural-language explanations without owning mandatory escalation policy.
14. As a team member, I want measured latency and false-trigger evidence before accuracy claims enter the presentation, so that our claims remain defensible.

## Implementation Decisions

- The highest test seam is a scripted care pipeline that consumes pose observations and returns an ordered timeline of event candidates and decisions.
- Pose observations contain normalized, derived motion data only. Raw video frames are outside the core-domain interface.
- The first event detector is explicitly a demo heuristic, not a clinical or statistical fall detector.
- A fall-like event requires an upright-to-horizontal transition, a downward center movement, sufficient landmark visibility, and a bounded transition interval.
- The event candidate confidence field is an evidence score generated by the heuristic. It must never be described as validated detection accuracy.
- The initial safety decision for a sufficiently supported `possible_fall` is a local check-in.
- A simulated `no_response` after check-in causes family notification.
- A positive `safe` response ends escalation.
- Low evidence produces manual review or no action rather than pretending certainty.
- MiMo is non-authoritative for mandatory safety escalation in the MVP. It may summarize observations, phrase prompts, or produce a human-readable explanation.
- The synthetic adapter is production-adjacent test/demo infrastructure, not evidence that offline video extraction works.
- The command-line demo prints structured JSON so that a later visual frontend can consume the same timeline.

## Testing Decisions

- Test behaviour through the scripted care-pipeline seam, not detector internals.
- A known upright sequence must emit no event and no escalation.
- A worked fall-like sequence must emit one `possible_fall`, then local check-in, then family notification after no response.
- A safe response must stop escalation.
- A low-visibility sequence must not emit a confident fall event.
- Running the synthetic demo in an empty temporary directory must not create raw image or video files.
- Contract serialization tests remain the prior art for explicit, JSON-safe domain outputs.
- Offline video extraction latency, CPU, memory, occlusion behaviour, and false triggers are measurements for the video-adapter spike, not unit-test assertions.

## Out of Scope

- Clinical diagnosis, emergency-service dispatch, or medical-device claims.
- Validated fall-detection accuracy.
- Face, identity, emotion, or activity recognition beyond the scripted MVP events.
- Multi-person or multi-room tracking.
- Cloud storage or forensic retention of raw video.
- A production mobile application.
- Real MiMo credentials or cloud calls in the first tracer bullet.
- Claiming Raspberry Pi 4B compatibility before measurement.
- Live camera capture in the MVP.

## Further Notes

The current environment is WSL2 and is sufficient for the motion-data core. The team will later provide an offline human video; that video will be used to validate a separate video-to-motion adapter. The minimum successful hackathon result is a truthful, visualizable motion-data pipeline and staged response flow, with extraction capability labelled unavailable until it has been measured on the supplied video.
